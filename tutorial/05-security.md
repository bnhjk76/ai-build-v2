# 第 5 章 安全：密码、会话与越权

> 学习线：☕ Java ｜ 对应真实文件：`server/src/main/java/com/ticketwallet/common/security/`、`domain/auth/`

## 5.1 密码永远不能明文存（哈希入门）

数据库里存的不是你的密码，而是密码经过 **Argon2 哈希**后的一串乱码：

```
注册密码 "Passw0rd!8"  ──Argon2──▶  {argon2}$argon2id$v=19$m=19456,t=2,p=1$盐$哈希值
```

特点：**单向**（算得过去、算不回来）、每次登录重新算一遍再比对。
本项目还实现了「降级路径」：万一 Argon2 库出问题，可切换 bcrypt，且两种格式的哈希能共存识别——真实系统的备胎思维。
（新手陷阱：不要自己发明「加密」，也不要用 MD5/SHA1——它们太快，容易被暴力破解。）

## 5.2 会话：登录状态存哪、怎么失效

用户登录后，服务器生成一个随机会话 ID 存进数据库表 `SPRING_SESSION`，并通过 **Cookie**（HttpOnly，JS 读不到）发给浏览器。之后每个请求浏览器自动带上这个 Cookie，服务器查表识别「你是谁」。

**退出登录 = 删除数据库里那一行**——立即失效，无法伪造。比 JWT（令牌）方案更适合本项目：改密码/踢下线立即生效。

## 5.3 越权：本项目最值得学的安全设计

问题：用户 A 能否用 URL `api/v1/invoices/{B的ID}` 看到用户 B 的发票？
**错误做法**：返回 403「无权限」——等于告诉攻击者「这个 ID 存在，只是不是你的」。
**本项目做法**：查询条件永远带上 `user_id = 当前登录者`，查不到就返回 404「记录不存在」——攻击者无法区分「不存在」和「不是你的」。

配套纪律：所有业务查询**必须**带 user_id 谓词（见 `InvoiceService.loadOwned()`），并有专门的「越权矩阵测试」（两个用户互相访问对方数据，断言 404 且响应里无他人数据痕迹）。

## 5.4 CSRF 与三道附件闸（纵深防御示例）

- **CSRF 双保险**：写接口必须带自定义头 `X-Requested-With`（恶意网站的表单提交带不上），外加 Cookie 的 SameSite=Lax；
- **附件三道闸**（顺序也有讲究）：① 格式（扩展名+文件头魔数，防改后缀的假图）→ ② 大小（>10MB 拒）→ ③ 数量（每条发票最多 3 个）。

> 魔数 = 文件开头的几个特殊字节（PNG 永远以 89 50 4E 47 开头），比扩展名诚实——把 `.zip` 改名 `.png` 骗不过它。

## 5.5 登录锁定（业务安全的经典案例）

连续 5 次密码错误 → 锁定 10 分钟，锁定期间**输对了也进不去**并告知剩余分钟。
实现时踩过一个极有教学价值的坑：把「计失败次数」和「抛出密码错误」包在同一个数据库事务里，结果抛异常时**事务回滚把计数也回滚了**——计数永远清零，锁定永不生效。
👉 教训：事务里做了「要留下的记录」又抛了异常，留下的也会被卷走。
