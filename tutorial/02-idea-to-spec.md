# 第 2 章 从一句话到一份蓝图：需求与设计

> 学习线：🤖 协作 + 产品思维 ｜ 对应真实文件：`WS/00_charter/charter.md`、`WS/01_product/`、`WS/02_design/`

## 2.1 一句话需求的正确打开方式

用户原话只有一句：「我想做一个网页版票夹管理，用户可以知道自己开过了哪些发票」。
直接开写代码会怎样？一周后你会做出一个「发票查看器」——而用户想要的是「台账」。
规划阶段做的第一件事是**把需求翻译成边界**（见 charter.md §2–§4）：

- **做什么**：注册登录、手工录入 11 个字段、多维筛选、汇总、导出 CSV、附件、回收站
- **不做什么（同样重要！）**：不接税务局接口、不做 OCR、不做 App、不做多人协作、不做进项发票

> 💡 新手提示：写「不做什么」的列表（叫**范围外**）比写「做什么」更能防止项目失控。

## 2.2 PRD：把功能写成可验收的句子

`WS/01_product/features.md` 用了 **MoSCoW 优先级**：

- **Must**：没有它 MVP 就失败（注册/登录/录入/列表/筛选/汇总/导出/回收站）
- **Should**：应该有（编辑、附件）
- **Could**：锦上添花（空态引导、抬头联想）
- **Won't**：明确不做

每个功能还配了 **Given-When-Then 验收标准**，例如「给定未注册邮箱，当提交注册，那么 201 并自动登录」。
这些句子第 7 章会直接变成自动化测试——**需求写得可测，测试才写得出来**。

## 2.3 设计先行：不写代码也能「设计」界面

`WS/02_design/design-spec.md` 里全是给工程师的**精确数值**（叫 Design Tokens）：

```css
--color-primary-500: #2B4CEE;  /* 主按钮的蓝 */
--radius-md: 8px;              /* 按钮圆角 */
--motion-fast: 150ms;          /* hover 动画时长 */
```

还有「状态设计」思维：每个页面除了正常样子，还要规定**加载中 / 空数据 / 出错 / 无权限**时长什么样。
页面清单 `pages.md` 给 8 个页面各定义了这 5 种状态——新手写页面最容易只写「快乐路径」，用户一旦断网就白屏。

## 2.4 本章最重要的一个概念：口径

「本月开了多少发票」这个数字，产品经理定义了精确口径（features.md 决策 A3）：
**有效金额 = Σ正常发票 − Σ红冲发票；作废的不计金额只计张数。**
没有这个口径，后端、前端、导出 CSV 三处各算各的，数字对不上——这是真实项目里最常见的 bug 来源之一。
