# 第 7 章 前后端「契约」与测试金字塔

> 学习线：🌐 Web + 工程实践 ｜ 对应真实文件：`contracts/openapi.json`、`server/src/test/`、`web/tests/e2e/`

## 7.1 契约链：AI 协作时代的护栏（也是人的护栏）

多个角色（本项目中甚至是多个 AI 会话）接力写代码，接口最容易漂移：后端改了字段，前端忘了改。本项目的解法是一条**单向流水线 + 三道防线**：

```
后端注解 ──工具生成──▶ contracts/openapi.json ──orval 生成──▶ 前端调用代码
                          （入库，代码一样被版本管理）
防线一：CI 重新导出契约并 diff——后端改接口没同步契约？红
防线二：CI 重新生成客户端并 diff——契约变了没重新生成？红
防线三：前端手写表单 schema 的类型必须能对上生成类型——字段名漂移？编译红
```

**真实事故**（第 9 个坑，值得讲给学生听）：一次删除了验证用的 spike 模块后，契约里两个同名 `CreateRequest` 发生覆盖，发票的创建参数类型被顶替——**防线三当场拦截**。这就是「让机器盯机器」的价值。

## 7.2 测试金字塔（本项目三层齐备）

| 层 | 工具 | 数量 | 跑一次 | 抓什么 bug |
| --- | --- | --- | --- | --- |
| 集成测试 | Spring 测试 + 真实 HTTP | 19 个 | ~5 秒 | 接口行为、错误码、越权、锁定 |
| E2E 端到端 | Playwright（模拟真人浏览器） | 34 个 | ~20 秒 | 页面流程、断网页脚、按钮禁用 |
| 性能测试 | 计时采样 | 1 个 | ~2 秒 | 慢查询（P95=31ms 达标） |

**新手最容易低估的是 E2E**：单元测试全绿 ≠ 用户能用。本项目 E2E 抓到过 4 个真实 bug：
① 前端请求路径拼了两次 `/api/v1/api/v1`（双前缀）——集成测试直连后端永远发现不了；
② 锁定后按钮文案被「处理中…」覆盖；
③ 桌面表格和移动卡片同时在页面里，测试脚本匹配到两个元素；
④ 并行测试用毫秒时间戳生成账号，撞号。
👉 每一个都不是「代码写错了」，而是「多个正确的零件组合出了错」——这正是 E2E 存在的意义。

## 7.3 一个 E2E 用例长什么样（R2 登录锁定）

```ts
test('连续 5 次失败后第 6 次锁定', async ({ page }) => {
  // …注册、退出…
  for (let i = 0; i < 5; i++) {
    await pwd.fill('WrongPass!9'); await btn.click()
    await expect(page.getByText('账号或密码错误')).toBeVisible()   // 断言统一文案
  }
  await pwd.fill('正确密码'); await btn.click()
  await expect(page.getByText(/账号已锁定，请 \d+ 分钟后重试/)).toBeVisible()
  await expect(page.getByRole('button', { name: /已锁定/ })).toBeDisabled()  // 断言按钮禁用
})
```

注意它断言的是**用户看得见的行为**（文案、按钮状态），不是内部变量——这正是验收标准（第 2 章）的直接翻译。

## 7.4 性能：先有预算，再谈优化

章程写明「1000 条内筛选 ≤1 秒」。测试脚本种 1000 条数据、采样 50 次算 P95（95% 的请求快于这个值——比平均值诚实）。实测 31ms，靠的不是缓存神技，只是**建对了索引**（第 4 章）。
