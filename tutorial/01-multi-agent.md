# 第 1 章 一个人的团队：多 Agent 协作全景

> 学习线：🤖 协作 ｜ 对应真实文件：`AGENTS.md`、`WS/project.json`、`WS/00_charter/`

## 1.1 为什么需要多 Agent

让 AI 写代码不难，难的是：**需求说不清、做出来的东西没人验收、改着改着就跑偏**。
多 Agent 协作的思路不是「更多 AI」，而是像公司一样**分工 + 流程 + 质检**：

- 每个 Agent 只扮演一个角色（产品经理、设计师、工程师……），职责单一，产出稳定；
- 角色之间**按依赖顺序传递文档**（设计师必须先读产品经理的 PRD 才能设计）；
- 每个阶段的产出都要过**质量门禁**，不合格就返工，兜底也要有记录。

## 1.2 本项目的角色流水线

```
总规划师(主Agent) → pm 产品 → designer 设计 → tech 技术
                                  ↓
              ops 运维 / support 客服 / finance 财务（依据 tech 与 pm 的文档）
```

每个角色交付什么？打开 `AGENTS.md` 第 2 节的表格看「必交文档」列——**这就是合同**。例如 pm 必须交 4 份：PRD、功能清单、用户故事、成功指标，缺一份或字数不够，主 Agent 就不验收、不入库、不进入下一阶段。

## 1.3 三个保证不跑偏的机制（本教程反复出现的主题）

**① 质量门禁**：文档必须存在、≥300 字节、有标题结构、全中文、不能是空壳模板。机器可判，杜绝「AI 糊弄」。
（真实实现：每个阶段结束跑一个校验脚本，见第 7 章测试理念——人和 AI 都需要被测试约束。）

**② 决策记录（D1–D7）**：所有「人才能拍板的事」显式记录。本项目真实记录了 7 条：

| 决策 | 内容 | 你能学到什么 |
| --- | --- | --- |
| D1 | 「忘记密码」纳入 M2 | 需求取舍要有记录，避免口头约定丢失 |
| D3 | 合规评估 | 数据敏感的产品要先评估法律风险 |
| D6 | 后端换 Spring Boot 技术栈 | **改技术栈 = 受控重跑**：重写文档→重导契约→全量回归测试，而不是推倒重来 |
| D7 | 引入 Lombok | 引新依赖前先做兼容性实验 |

**③ 知识库**：每份文档入库时打标签建索引，后续任何角色/项目都能检索复用——这就是「组织记忆」。

## 1.4 新手最容易误解的一件事

多 Agent ≠ 完全自动。本项目中人类做了 4 件事：提出需求、拍板 7 个决策、提供环境（装好 JDK/Docker）、验收最终产品。**AI 负责体力与初稿，人负责方向与判断**——这个分工本身就是你要学的第一课。
