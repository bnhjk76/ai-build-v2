## 1. 背景

票夹通由多个开发会话接力实施、单机部署、trunk-based 分支（engineering-plan §3）。CI/CD 的目标不是「炫技式全自动化」，而是三件朴素的事：**合入 main 前把住质量与安全门禁、从 tag 到生产一键可重复、发布出问题 5 分钟内自动退回**。对应 pm 设定的质量指标——核心接口 P95 <500ms、可用性 ≥99.5%——本方案在流水线中以夜间性能基线与发布健康门禁承接。

选型：GitHub Actions（或等价 CI）三 job 并行 + SSH 单机部署。不为单机制度引入 K8s/GitOps/Argo 等复杂度（tech-stack T1）。

## 2. CI 流水线阶段

### 2.1 PR 触发（合并前置，全绿才可合入 main）

```mermaid
flowchart LR
    PR["PR（feat/* fix/*）"] --> L["① lint<br/>web: eslint+prettier<br/>server: checkstyle"]
    L --> T["② typecheck<br/>tsc --noEmit（含防线三）"]
    T --> U["③ unit<br/>web: Vitest / server: JUnit 5"]
    U --> I["④ integration<br/>Testcontainers PG + 契约 diff（防线一/二）"]
    I --> B["⑤ build<br/>pnpm build + mvnw package + 镜像验证"]
    B --> E["⑥ e2e-smoke<br/>R2/R3/R4 chromium"]
    E --> S["⑦ 安全固定项<br/>五项（§3.3）"]
    S --> M["合并 main<br/>（squash）"]
```

各阶段要点：

| # | 阶段 | 内容 | 并行策略 |
| --- | --- | --- | --- |
| ① | lint | web：eslint + prettier --check（0 error 0 warning）；server：`./mvnw checkstyle`（轻量风格门禁，tech-stack §8） | **web / server 两 job 并行**；web 缓存 pnpm store，server 缓存 Maven `~/.m2` 仓库（engineering-plan §5） |
| ② | typecheck | web `tsc --noEmit`（generated 类型对手写代码的编译期约束）；**契约防线三**：手写 zod 表单 schema 输出类型 `satisfies` 生成请求类型的对齐单测（tech-stack §7.3） | web job |
| ③ | unit | web：Vitest（mask/money/筛选序列化/zod 规则）；server：JUnit 5 + AssertJ（口径 A3、掩码、金额序列化、CSV 转义、锁定计数、daysLeft） | 两 job 各自执行 |
| ④ | integration | server：`./mvnw verify`——@SpringBootTest + MockMvc + **Testcontainers（PG16 真库）**，覆盖 api-design §4 全接口与错误码断言、越权矩阵；**契约防线一**：verify 中 springdoc 导出 `contracts/openapi.json` → `git diff --exit-code`；**契约防线二**（web job）：重跑 `pnpm gen:api` → `git diff --exit-code web/src/api/generated/` | server job 内串行（共享测试库）；Testcontainers 需 Docker runner，不可用时降级为 PG service 容器（engineering-plan §7 R8） |
| ⑤ | build | `pnpm build`（web 产物）+ `./mvnw package`（server 分层 jar）+ Docker 镜像构建（api 多阶段：maven 构建层 → temurin-25-jre-alpine；不推送，仅验证 Dockerfile 可用） | 两 job 汇聚后执行 |
| ⑥ | e2e-smoke | Playwright chromium：R2 登录 / R3 录入 / R4 筛选（含越权 404 与 CSRF 头断言） | build 后执行 |
| ⑦ | 安全固定项 | §3.3 五项 | 与 ⑥ 并行 |

### 2.2 夜间触发（main，每晚 02:30 东八区）

1. **全量 E2E**：R1–R10 全部 spec，chromium + webkit、375px 与 1280px 双视口（engineering-plan §4.2 映射表）；
2. **性能基线**：k6 脚本，1000 条种子数据组合筛选，阈值 P95 <500ms；**连续两次超标才告警**（防抖动误报），告警走 monitoring.md §5 的 P1 通道；
3. **契约一致性 diff**：springdoc 导出的 `contracts/openapi.json` 与 api-design.md 契约全量 diff，漂移即红灯（PR 防线一拦增量，夜间全量兜底；api-design §8.2 行动 1）；
4. **依赖 CVE 周扫（每周一次，v1.1 新增）**：server `./mvnw dependency-check`（OWASP 插件）+ web `pnpm audit`，高危 48h 内升级或 pin（engineering-plan §6.3 依赖风险条款）。

## 3. 质量门禁

### 3.1 阈值总表（任一不满足即阻塞合并）

| 门禁 | 阈值 | 检测位置 |
| --- | --- | --- |
| lint | 0 error / 0 warning（web eslint+prettier、server checkstyle） | CI ① |
| typecheck | 0 error（含 generated 类型约束与防线三对齐单测） | CI ② |
| **契约防线一** | `git diff --exit-code contracts/openapi.json` 无漂移（后端改接口未同步导出契约即红） | CI ④ server job |
| **契约防线二** | `git diff --exit-code web/src/api/generated/` 无漂移（契约更新未重新生成客户端即红） | CI ④ web job |
| **契约防线三** | 手写 zod schema 与生成类型 `satisfies` 对齐编译通过 | CI ② |
| 单测行覆盖 | ≥80%（server common/domain service 与 web 工具函数） | CI ③，coverage 报告留档 |
| 集成用例 | api-design §6 **每个错误码至少 1 个用例**；P0 接口（auth/invoices）全覆盖；Testcontainers 真库（pg_trgm/部分索引/enum 与生产同构） | CI ④ |
| E2E smoke | R2/R3/R4 全绿 | CI ⑥ |
| 安全固定项 | §3.3 五项全绿 | CI ⑦ |
| PR 规范 | 关联 features.md 至少一条验收编号（描述含 Given/When/Then）；**接口变更 PR 必含 `contracts/openapi.json` 与 `web/src/api/generated/` 同步更新** | 人工评审 + 模板校验 |
| 分支生命周期 | feat/fix 分支 ≤3 天，超期机器人提醒归并 | 仓库规则 |

### 3.2 门禁豁免纪律

- **不设 skip 标志旁路**：任何阶段红灯必须修复或回退代码，不允许 merge admin 绕过；
- 唯一例外：`pnpm audit` / `./mvnw dependency-check` 高危 CVE 刚披露、上游尚无修复版本时，可开 issue 记录并 pin 版本（48h 复查，engineering-plan §6.3 依赖风险条款），豁免须在 PR 描述引用 issue 号。

### 3.3 安全测试固定项（每次 PR 必跑，任一红即阻塞）

1. **ownership 越权矩阵**：4 类资源（发票详情/编辑/删除/附件）× 2 用户交叉访问，全部断言 `404 INV_001`（F07 验收第 4 条，server 侧 `OwnershipMatrixTest` 集成用例）；
2. **会话失效**：登出/过期的 session Cookie 重放业务接口，断言 `401 AUTH_003`（Spring Session 登出删行语义验证，engineering-plan §4.3 第 2 项）；
3. **上传魔数绕过尝试**：`.zip` 改后缀 `.pdf`、伪造扩展名文件，断言 `422 ATT_003`；
4. **CSRF 头校验（v1.1 新增）**：写接口（POST/PATCH/DELETE，`/api/v1` 下）不携带 `X-Requested-With: XMLHttpRequest` 头，断言 `403 AUTH_006`（engineering-plan §4.3 第 4 项）；
5. **密钥泄漏扫描**：`.gitignore` 白名单校验（`.env` 不入库）+ 提交内容 grep 密钥特征（`SPRING_DATASOURCE_PASSWORD`、DB 连接串、备份凭证模式）。

## 4. 制品与版本

1. 镜像命名 `tw-api:v{tag}` / `tw-web:v{tag}`，tag 即 git tag（`v{里程碑}.{序号}`，如 v1.0.0=M1 首个验收版），**禁止 latest 部署生产**；tw-api 构建口径：多阶段构建（`maven:3.9-eclipse-temurin-25` 构建层 `./mvnw package` → `eclipse-temurin:25-jre-alpine` 运行层 + Spring Boot 分层 jar），目标体积 <350MB（tech-stack §6.2）；tw-web 产物构建期注入 caddy 镜像（architecture §2）；
2. 镜像推送到 GHCR（免费档）；生产保留**最近 3 个 tag**，更早的由定期任务清理；
3. 制品与迁移绑定：Flyway 迁移脚本（`db/migration/V*.sql`）随 jar 打包进 api 镜像，容器启动时自动 migrate（deployment.md §4 步骤 6）；迁移文件随代码同 tag，迁移状态在 PG `flyway_schema_history` 表（镜像内不含状态）；
4. **JDK 21 回退位（W1 spike 失败场景，v1.1 新增）**：若 M1 W1 spike 判定 Boot 4.1.1 × JDK 25 组合不可行并决策回退 JDK 21（engineering-plan §6.2 第 3 条），仅改 `pom.xml` 的 `<java.version>` 与镜像基座（`temurin-21-jre-alpine`）重新出 tag——流水线阶段、质量门禁、发布与回退流程**零变化**（应用代码不感知）；回退后的首个 tag 须在发布日志注明 JDK 基线变更。

## 5. 发布策略（CD）

### 5.1 策略选择：单机「健康门禁式滚动发布 + 自动回退」

单机无负载均衡，**不具备真蓝绿/金丝雀双活条件**（违反 T1 不扩容的前提下），采用最接近的组合：

| 策略要素 | 本项目做法 |
| --- | --- |
| 发布单位 | git tag → 镜像 tag，一键可重复 |
| 停机窗口 | api 容器重建 <10 秒（PG 与数据卷不动，用户仅感知一次请求重试）；发布窗口固定 **每周四 21:00–22:00（东八区）**，避开记账高峰 |
| 滚动 | compose 只重建 api/caddy，postgres 容器不动（deployment.md §5.1） |
| 灰度 | M3 W6 试运行 7 天 = 真实用户灰度（真实数据录入 + 性能观测，engineering-plan §2.2）；正式运行后无多实例灰度条件，靠 staging 预演替代 |
| 回退 | 部署后拨测 30 秒内不通 → **自动回退上一 tag**（§5.2 步骤 6） |

### 5.2 CD 流水线步骤（tag push 触发）

1. CI 全量复跑（同 §2.1 七阶段，作为发布前最后一道）；
2. 构建并推送 `tw-api:v{tag}`（Maven 多阶段构建 + 分层 jar，见 §4 第 1 条）/ `tw-web:v{tag}`；
3. SSH 到生产机，**部署前自动 `pg_dump`** 落 `/data/backups/pre-deploy-{tag}.dump`（先备份后迁移，engineering-plan §6.2）；
4. `docker compose pull` → `docker compose up -d api`：**Flyway 随 api 启动自动迁移**，`docker logs -f tw-api` 确认 `Successfully applied` 后继续（迁移失败即中止并按 deployment.md §5.2 回退；**生产禁用 `flyway clean`**）；
5. `docker compose up -d`（重建 api/caddy）；
6. **健康门禁**：每 5 秒拨测 `GET /api/v1/health` 共 6 次（30 秒窗口），任一非 200 → 自动改回上一 tag 镜像 `up -d` 并再验证 → 通知失败告警；
7. 发布通知：推送结果（tag、耗时、Flyway 迁移版本、健康检查结论）到值班频道，写入发布日志。

### 5.3 发布纪律

1. 生产发布只允许从 `release/{tag}`（M3 起）或 main 的 tag 触发，禁止从 feat 分支直达生产；
2. 数据库迁移（Flyway `V*.sql`）必须**先经 staging 全量验证**（含失败回滚演练：恢复 pre-deploy dump 后迁移可重放）方可上生产；
3. 紧急修复（hotfix）：从 main 拉 `fix/{issue}` → 走完整门禁 → 新 tag 发布，**不允许跳过门禁的「紧急直推」**；
4. 每次发布后 30 分钟内人工冒烟（登录/录入/列表/导出四链路），结果回填发布日志。
