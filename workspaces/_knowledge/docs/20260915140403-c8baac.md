## 1. 背景

票夹通是个人/小微场景的单机服务，监控方案的第一原则是**与规模匹配**：不部署 Prometheus/Grafana 全家桶（违反 tech-stack T1，月成本也超 T5 的 ¥50 红线），采用「**外部拨测 + 结构化日志 + 每日巡检脚本**」三层轻量组合，兑现 M3 DoD 的「健康检查 + 拨测 + 告警通道」与「99.5% 可用性拨测基线」。可选增强项（Sentry 免费档）单独列出，默认不启用。

监控必须回答的四个问题（四个黄金信号）：

1. 服务活着吗？（可用性）
2. 用起来快吗？（延迟——pm 指标：核心接口 P95 <500ms）
3. 出错了吗？（错误率）
4. 机器还扛得住吗？（饱和度——单机最易死于此）

## 2. 核心指标

### 2.1 指标总表（信号 → 指标 → 阈值 → 告警级别）

| 信号 | 指标 | 采集来源 | 正常值 | 告警阈值（级别） |
| --- | --- | --- | --- | --- |
| 可用性 | `GET /api/v1/health` 拨测成功率（月度） | UptimeRobot 5 分钟间隔 | 月度 ≥99.5%（=月停机 ≤3.6h，对齐 pm 指标） | 连续 2 次失败（**P0**）；月度累计成功率跌破 99.5%（P1，月末核算） |
| 延迟 | 核心 API P95（auth/invoices 列表/stats） | logback JSON 日志 `durationMs` 字段，每日巡检脚本聚合昨日 | P95 <500ms；列表筛选端到端 ≤1s（G2） | P95 >500ms 持续 10 分钟（P1）；夜间 k6 基线连续两次超标（P1，cicd.md §2.2） |
| 错误率 | 5xx 比例（按分钟） | logback JSON 日志 level=error 计数 | <0.1% | >1% 持续 5 分钟（P1）；>5% 持续 5 分钟或 health 503（**P0**） |
| 饱和度 | 宿主 CPU 使用率 | 每日巡检脚本（07:30）+ `docker stats` | <70% | >85% 持续 5 分钟（P1） |
| 饱和度 | 宿主内存使用率 | 同上 | <80%（2GB 机器，常态约 60%） | >90%（P1）；触发 OOM kill 事件（P0） |
| 饱和度 | **api 容器 RSS（JVM 进程驻留内存，v1.1 新增）** | 每日巡检脚本 + `docker stats` | ≤550MB（tech-stack §6.2 预算，容器 limit 768MB） | >600MB 持续 10 分钟（P2 预警）；>660MB（≈limit 85%，P1）；容器被 OOM kill（**P0**，runbook F11） |
| 饱和度 | **JVM 堆占用 / GC 停顿（SerialGC，v1.1 新增）** | 巡检脚本读内网 Actuator metrics（`jvm.memory.used` / `jvm.gc.pause`；未启用时以 RSS 兜底，§2.2 第 4 条） | 堆稳态 ≤345MB（堆上限 460MB 的 75%，`MaxRAMPercentage=60`）；Full GC <1 次/小时 | Full GC >5 次/小时或单次停顿 >1s（P2，runbook F11）；启动即 OOM（**P0**） |
| 饱和度 | 磁盘使用率（40GB SSD，含附件卷） | 同上 | <75% | >75%（P2）；>85%（P1）；>95%（**P0**——附件写满即业务不可写） |
| 饱和度 | PG 连接数 / 上限 | 巡检脚本 `pg_stat_activity` 计数 | <5（api 侧 HikariCP 池 10 的一半以下；PG max_connections=30） | >8（池上限 80%，P2） |
| 业务 | 登录失败次数（同 IP） | logback JSON 日志 auth 模块计数 | 个位数/天 | 同 IP >50 次/10 分钟（P1，暴力破解，联动 runbook §7） |
| 业务 | 附件上传失败率 | logback JSON 日志 ATT 错误计数 | ≈0 | >10%（P2，磁盘/权限，runbook §5） |
| 业务 | 回收站清理 cron 执行 | @Scheduled 任务完成日志（logback） | 每小时 1 条完成记录 | 连续 24h 无执行记录（P2，F12 兑现风险） |
| 业务 | 备份任务结果 | 备份脚本退出码（backup-dr.md §3） | 每日 1 成功 | 失败或产物缺失（P1——数据安全底线） |
| 业务 | CSV 导出失败（EXP_001 之外的 5xx） | logback JSON 日志 | ≈0 | 单日 >5 次（P2） |

说明：

1. 阈值口径与 pm 质量指标（P95 <500ms、可用性 ≥99.5%）严格对齐，**阈值即验收线**；
2. 「持续 N 分钟」类阈值由巡检脚本/拨测平台的连续采样判定，避免单点抖动误报；
3. health 端点语义遵循 api-design §4.6：DB 不可达返回 503——拨测因此同时覆盖「进程活」与「DB 连得上」两层；
4. JVM 两行为 v1.1 新增（技术栈对齐）：RSS 阈值与 tech-stack §6.2 预算对齐（550MB 目标 / 768MB limit）；GC 指标采集依赖内网 Actuator 通道（§2.2 第 4 条），未启用时以容器 RSS 与重启计数兜底。

### 2.2 健康检查实现要求（开发会话落地项）

1. `GET /api/v1/health`：**自写 controller**（tech-stack §3.10，不使用公网 Actuator health），无认证，`200 {status:"ok", db:"up"}` / `503`；内部执行 `SELECT 1` 探 DB——**端点路径与语义 v1.1 对齐后不变**，仅实现载体由 NestJS 换 Spring Boot；
2. Compose 层 healthcheck：api 容器每 30 秒自检 `/api/v1/health`（容器内 wget），连续 3 次失败标记 unhealthy；postgres 容器用 `pg_isready`；
3. 拨测只打 health 端点，**不触碰业务数据**（architecture §2 要点 3）；
4. **JVM 指标内网通道（v1.1 新增）**：如开发侧启用 Actuator metrics（`/actuator/metrics/jvm.memory.used`、`jvm.gc.pause` 等），仅绑定 compose 内网，Caddy **不反代 `/actuator/*`**（公网不可达——tech-stack §3.10「不暴露完整 Actuator 端点到公网」；`/v3/api-docs` 同步屏蔽，engineering-plan §2.2 W6）；巡检脚本经 `docker exec` 或内网 curl 采集；未启用时以 `docker stats` RSS 兜底。

## 3. 日志方案

### 3.1 格式与规范（logback JSON，v1.1 由 pino 对齐）

每行一个 JSON 对象（logback + logstash-logback-encoder，tech-stack §3.10），核心字段：

```json
{"level":"info","time":"2026-09-14T09:30:00.123+08:00","requestId":"a1b2c3","module":"invoices","msg":"list ok","status":200,"durationMs":37,"userId":"8f3c…"}
```

1. `requestId` 由 `RequestIdFilter` 写入 MDC 并回写响应头 `X-Request-Id`（architecture §7）——support 拿用户报错截图中的 requestId 即可精确反查这一行及上下游日志（api-design §6 规范细则 1）；
2. `durationMs` 供延迟聚合（§2.1）；错误日志附 `err`（含堆栈，但**响应体永不带堆栈**）；
3. **敏感纪律（G4）**：不落密码、不落全号（掩码后可落 `****5678`）、不落 Cookie/session ID；CI 固定项扫描日志语句（cicd.md §4.2）。

### 3.2 存储与保留

| 项 | 方案 |
| --- | --- |
| 容器日志 | Docker `json-file` 驱动：`max-size=50m, max-file=4`（api/caddy/pg 三容器约 600MB 上限） |
| 保留期 | 滚动保留 14 天（与备份保留期对齐）；超期由 rotate 清理 |
| 检索 | 常规：`docker logs --since 1h tw-api 2>&1 | grep '"requestId":"a1b2c3"'`；跨天：`/data/backups/logs/` 归档目录 grep；**不引入 ELK**（数据量级不值） |
| 归档 | 每日 02:00 备份任务顺带打包前一日日志 gzip 归档（backup-dr.md §3） |

### 3.3 每日巡检脚本（07:30 东八区，ops 维护，放宿主 crontab）

输入=昨日日志与系统指标，输出=一条汇总推送（渠道见 §5）：

1. 磁盘/CPU/内存/PG 连接四项快照与阈值比对；
2. **api 容器 RSS 与 JVM 堆/GC 快照（v1.1 新增）**：`docker stats`（RSS 对照 550MB 预算）+ 内网 Actuator metrics（堆占用、GC 停顿），连续 3 日趋势随汇总推送，超 §2.1 阈值按级别告警；
3. 昨日 5xx 计数、P95 采样（auth/invoices/stats 三模块 durationMs 聚合）；
4. 回收站 cron 执行记录数、附件上传失败计数；
5. 昨日备份产物存在性与大小（联动 backup-dr.md §5）；
6. 证书剩余有效期（`acme` 目录 mtime 或 openssl 探测，见 runbook §2）。

## 4. 拨测

1. UptimeRobot 免费档：`GET https://<域名>/api/v1/health`，5 分钟间隔；
2. 判定：连续 2 次失败才告警（防单次网络抖动）；恢复时发恢复通知；
3. 月度成功率报表即「99.5% 可用性」的验收数据源（M3 试运行期建立基线，engineering-plan §2.2 W5 DoD）。

## 5. 告警规则与分级

### 5.1 分级定义与响应时效

| 级别 | 定义 | 响应时效 | 处置要求 |
| --- | --- | --- | --- |
| **P0** | 服务不可用/数据不可写/安全事件：health 连续失败、5xx>5%、磁盘>95%、OOM、疑似数据泄露 | **15 分钟内响应** | 立即按 runbook 处置；15 分钟内无法修复 → 回滚（deployment.md §5）或重启；事后 24h 内复盘 |
| **P1** | 核心体验受损/数据安全前置风险：P95 超标、磁盘>85%、备份失败、暴力破解、5xx>1% | **4 小时内响应** | 当日定位根因；修复或给出规避方案 |
| **P2** | 边缘异常/容量预警：磁盘>75%、单次 cron 失败、附件失败率>10%、连接数偏高 | **当日内处理** | 进 issue 池，随例行发布解决 |

### 5.2 通知渠道与路由

| 渠道 | 承载 | 配置 |
| --- | --- | --- |
| UptimeRobot → 邮件 + App push | 可用性 P0/P1 | 免费档自带 |
| 钉钉/企业微信**群机器人 webhook** | 巡检脚本汇总、备份结果、P1/P2 项 | 巡检脚本失败分支直接 @所有人（仅 P0/P1 时） |
| 短信（可选） | P0 升级（30 分钟未响应时） | 运营商免费额度或放弃（成本纪律） |

路由规则：所有 P0 同时走邮件 + 群机器人 @；P1 走群机器人；P2 只进每日汇总（不打扰）。

### 5.3 值班与升级路径

1. 单人项目：值班人=ops（本人），support 为工作时段第一响应备份；
2. 升级链：**值班 ops（15 分钟）→ tech（代码/架构级，30 分钟）→ 决策回滚/停服（pm 或 owner）**；
3. 每次告警处置后在 runbook 附录的《故障记录表》登记（时间/级别/根因/耗时/动作），月度回顾 P0/P1 趋势。

### 5.4 可选增强（默认不启用，触发条件列出）

Sentry 免费档接入前端错误（React ErrorBoundary + 上报）：当试运行期出现「用户报告前端异常但日志无对应 5xx」≥3 次时启用；启用后仅上报错误堆栈 + 脱敏上下文，与 G4 日志纪律一致。
