## 1. 背景

### 1.1 Monorepo 形态论证：目录并列（Maven + pnpm 共存），不用 Gradle 多模块统一

后端换 Java 后存在两种 monorepo 组织方式：

| 方案 | 描述 | 取舍 |
| --- | --- | --- |
| A. Gradle 多模块统一（server / web 均为 Gradle 模块，前端经 Gradle node 插件驱动） | 一个构建工具管两端 | **放弃**：①构建工具本已论证选定 Maven（tech-stack §3.2），推翻无据；②用构建工具包装 pnpm 会引入「两层包管理 + 一层构建胶水」，AI 会话排查成本高；③前后端发布节奏独立（契约工件为耦合点），统一构建反而制造全量构建依赖 |
| **B. 目录并列（选定）** | `server/` 为自足的 Maven 项目（自带 mvnw/pom.xml），`web/` 为自足的 pnpm 项目（自带 package.json），根目录无构建脚本仅 README 与约定；两区由 `contracts/openapi.json` 契约工件耦合 | **选定**：①每区工具链原生、会话可独立认领（Java 会话只看 server/，前端会话只看 web/）；②契约耦合显式可见（改动必经 contracts/，CI 有 diff 检测）；③CI 按 目录分 job 并行，缓存互不干扰 |

配套约束：**契约工件是唯一耦合点**——server 改接口必导出 contracts/openapi.json，web 必重新 orval 生成，CI 三道防线拦截（tech-stack §7.3）；除 contracts/ 外，server 与 web 互不引用对方任何文件。

### 1.2 目录规划三规则（继承 v1.0）

1. **目录即架构**：后端六业务域（architecture §4.1）一一对应 `domain/` 下六个包目录，前端 `features/` 与之镜像，任何会话可按目录认领模块；
2. **收敛不动点**：跨域复用物（横切安全/错误/日志/存储、7 个通用组件、脱敏/金额/校验工具）各有唯一归属目录，禁止在业务目录私建副本；
3. **测试同构**：Java 测试走 Maven 标准位（`src/test/java`），前端单测紧邻源码（`*.test.ts` 同目录），E2E 集中 `web/tests/e2e/`。

## 5. 约束与纪律（写给后续开发会话）

1. **不新增顶层目录**：如确需（如独立 worker），须经主 Agent 变更本文件并升版本号；
2. `domain/*` 包之间**禁止横向引用**（recycle 对 invoices 的委托经 service 接口注入；attachments 联动同理）——保证模块可独立测试；`common/` 不得反向依赖 `domain/`；
3. `web/src/components` 仅放 design-spec §5 清单内 7 件，业务组件一律进 `features/*`；
4. **`web/src/api/generated/` 与 `contracts/openapi.json` 均为生成物/工件**：前者只能由 orval 产出、后者只能由 springdoc 导出，**禁止手改**（CI diff 会拦截）；接口变更必走「改注解 → 导出 → 生成 → 提交」四步；
5. Java 包内二级子包（`common/security/` 等）物化时不建、实现时创建，但**包名必须与本文 §3 表格一致**，防止会话间命名漂移；
6. 测试文件与被测对象同名（`mask.ts` ↔ `mask.test.ts`；`InvoiceService` ↔ `InvoiceServiceIntegrationTest`）；E2E 文件名前缀 `r{编号}` 对应 interactions 流程编号；
7. `server/` 与 `web/` 除经 `contracts/` 外互不引用文件；跨区脚本调用（如导出契约后触发 orval）只能放在根级 `Makefile`/`scripts/`，不写进任何一区的构建配置。
