# 反馈闭环 —— 票夹通（TicketWallet）

> 文档版本：v1.0 ｜ 撰写日期：2026-09-14 ｜ 撰写角色：support（客服负责人）｜ 状态：待评审

## 1. 背景

客服体系不只是「答疑」，更是产品免费阶段最重要的**需求与缺陷传感器**：用户量小、无商业化指标牵引时，反馈数据是决定二期方向（章程范围外六项何时解冻、Q1 忘记密码是否补入 M2）的关键输入。本文定义反馈「从哪来、怎么分级、流到哪去、多久闭环」四件事。

本项目是团队知识库的**首个项目**：所有沉淀从零建立，本项目上线后的 FAQ 与高频问题将构成知识库的初始条目（见 §4.5）。

## 2. 反馈收集渠道

| # | 渠道 | 形式 | 说明 |
| --- | --- | --- | --- |
| 1 | 人工客服会话 | 客服邮箱 / 登录页客服入口（pm 预留位） | 一切人工交互中出现的建议/不满/异常，由客服按 §3 分级登记 |
| 2 | 工单 | ticketing §2 规范 | P3 类天然是反馈；P0–P2 处置后的根因归类也是反馈 |
| 3 | FAQ 页反馈入口 | 「没解决？告诉我们」链接（占位，随 FAQ 页上线） | 低摩擦轻反馈，默认匿名 + 可留联系方式 |
| 4 | 被动信号（无需用户开口） | 埋点失败事件 + 错误码频次统计 | 见下 |

**被动信号清单**（事件源：metrics 埋点字典与 api-design 错误码）：

- `account_login_fail{reason:locked}` 频次高 → 大量用户触发锁定：密码记忆困难 + 无自助找回，直接佐证 Q1（忘记密码）优先级；
- `invoice_create_fail{reason:validation}` 按字段聚合 → 某字段（如发票号码位数）行内报错高频 = 表单可用性问题，回流 designer；
- `export_fail{reason:over_limit}` 多次出现 → 用户数据量接近 5000 条上限，回流 pm 评估导出能力；
- `attachment_upload_fail{reason:oversize / count_limit / format}` 各 reason 占比 → 决定 FAQ 重点与压缩引导优化；
- SYS_001 / SYS_002 出现频次与时段聚类 → 回流 tech/ops（结合 X-Request-Id 日志）；
- 空态曝光 `empty_state_view` 高但首录转化低 → 新用户引导问题，回流 designer/pm。

被动信号周度拉取一次（MVP 手动，量级小），阈值见 §3.3。

## 3. 反馈分级规则

### 3.1 类型 × 影响二维定级

**类型**（四类）：

| 类型 | 定义 | 去向 |
| --- | --- | --- |
| A 缺陷 | 系统行为与验收标准不符（错误码异常出现、功能失效、数据错误） | tech（issues） |
| B 功能建议 | 请求新增能力（含章程范围外六项：查验/OCR/App/协作/进项/支付） | pm（二期评估池） |
| C 体验与文案 | 交互困惑、文案歧义、空态引导不足 | designer |
| D 口径咨询 | 汇总口径、脱敏边界、回收站规则等理解类 | faq.md 更新 |

**影响**：沿用工单 P0–P3（ticketing §3）——反馈本身不另行发明等级，保证全体系一套语言。

**合并定级示例**：用户反馈「希望拍照识别发票」= B 类 × P3（体验增强）→ pm 二期池，且直接关联章程 O2。

### 3.2 去重与高频标记

- 同一主题（语义相同）7 日内合并计数到一条主反馈，附「提及次数」；
- **提及次数 ≥ 3 → 标记「高频」**，进入当周回流清单必议项；
- 高频反馈在 FAQ 对应条目上加挂「已有较多用户提出」内部注记（不外发）。

### 3.3 被动信号阈值（周检）

| 信号 | 阈值（周） | 动作 |
| --- | --- | --- |
| locked 登录失败 | ≥ 10 次 | 立即列入 Q1 催办证据，pm 通报 |
| 同字段 validation 失败 | ≥ 20 次 | C 类高频，回流 designer |
| over_limit 导出失败 | ≥ 3 次 | B 类，回流 pm |
| SYS_001 聚类 | 任何聚类 | A 类，直接建 P2 工单转 tech |

## 4. 回流机制（流向、载体、时效）

### 4.1 A 缺陷 → tech

- 载体：开发 issues（含工单号引用）；
- 必附信息：X-Request-Id、错误码、复现步骤、截图、浏览器/设备、影响人数（提及次数）；
- 时效：P0/P1 级缺陷**即时**转值班（不等周批）；其余随周批。

### 4.2 B 功能建议 → pm

- 载体：pm 维护的二期评估池；
- 对接点：①章程范围外清单 O1–O6（用户诉求为解冻证据）；②PRD 待确认 Q1（忘记密码）、Q2（抬头脱敏）——**每次忘记密码人工受理（sop §5.1）都计入 Q1 证据链**；
- 时效：周批；「高频」标记项在回流会必议。

### 4.3 C 体验文案 → designer

- 载体：设计改进清单；
- 时效：双周批（与 designer 迭作节奏对齐）。

### 4.4 D 口径咨询 → faq.md

- 同一口径问题周内出现 ≥ 3 次 → 当周新增/修订 FAQ 条目并升 faq 版本号；
- 若暴露的是产品口径本身歧义（如汇总口径 A3 用户普遍误解）→ 同步 pm 判定是「解释不够」还是「口径需改」，后者走变更管理（features §5）。

### 4.5 高频问题 → 知识库沉淀（首个项目，从零建库）

- 每月把「高频 FAQ 条目 + 典型工单处置记录」沉淀为知识库条目，条目结构：`问题摘要 / 标准话术 / 关联错误码与功能 ID / 更新时间`；
- 本项目条目构成知识库初始集合，后续项目客服角色优先检索复用再增量撰写；
- 机器人上线后，知识库条目 + faq.md Q/A（Q 编号作 intent id）共同构成语料基线。

### 4.6 回流节拍总表

| 节拍 | 动作 | 责任 |
| --- | --- | --- |
| 即时 | P0/P1 缺陷与安全事件转值班 | 一线客服 → L3 |
| 每周（T+1 汇总上周） | A/B 类反馈分流（issues / pm 池）、被动信号周检、FAQ 增补 | support |
| 双周 | C 类批送 designer；回流会（support+pm+tech+designer 各 30 分钟）过「高频」清单 | support 召集 |
| 每月 | 知识库沉淀；反馈月报报主 Agent（含 §6 指标、TOP5 问题、Q1 证据链计数） | 客服负责人 |

## 5. 对用户的闭环（让反馈可感知）

- 提交反馈后回执话术：

  > 感谢你的建议，已记录编号 {编号}。我们每周集中评估一次反馈，功能类建议会在评估后给你答复；如需跟进，可直接回复本邮件引用该编号。

- 被采纳并上线的反馈：上线公告中归功致谢（「来自用户的需求」）；原反馈用户获一对一通知（B 类高频项必做）；
- 不采纳的（与章程范围冲突）：话术说明当前边界并告知「已进入二期评估池」，不做「永远不会做」的表述。

## 6. 度量

| 指标 | 定义 | 目标（上线后首个季度） |
| --- | --- | --- |
| FAQ 自助解决率 | FAQ 页浏览后 24h 内未产生同主题人工工单的占比 | ≥ 60% |
| 工单率 | 每 100 注册用户月工单量 | 趋势下降 |
| 反馈转化率 | 反馈被采纳（进入排期/上线/FAQ 沉淀）的比例 | ≥ 20% |
| TOP5 重复问题占比 | 月度工单 TOP5 主题占全部工单比例 | 环比下降（验证 FAQ 有效） |
| 闭环时长 | 反馈提交 → 得到明确去向（采纳/排期/不采纳）的中位天数 | ≤ 14 天 |
