> 文档版本：v1.0 ｜ 撰写日期：2026-09-14 ｜ 撰写角色：compliance（AI 辅助） ｜ 状态：待主 Agent / 用户确认

## 1. 背景

D3 决策将合规评估前置于 M1 开发启动前，目的正是「评估结论反向影响存储与展示设计，避免返工」。评估结论（legal-assessment.md §7）：缺口集中在**告知同意体系、账号注销（删除权）、静态存储加密**三处，其中 P0 级整改必须在 M1 范围内吸收（涉及注册接口与数据结构，后补成本高）；其余按 M2/M3 节奏排布。

优先级定义：

- **P0 = M1 开发启动前定稿方案、M1 内落地**（影响 M1 接口/表结构/部署基线，延后即返工）；
- **P1 = M2 范围吸收**（功能开发类）；
- **P2 = M3 上线前完成**（发布门禁类或需人工决策）。

## 3. 整改项明细（映射文档修改位置 + 验收标准）

### T1（P0）注册同意流程

**解决的问题**：R2——处理个人信息缺告知同意环节，违反个保法第 13/17 条、网安法第 41 条。

**修改位置**：

1. `01_product/features.md`：新增功能条目（F 编号顺延）「注册同意」，含验收标准「未勾选同意不可提交注册；同意版本与时间留痕」；
2. `01_product/PRD.md` §6.1 MVP 能力清单第 1 条补充「注册需勾选同意隐私政策与用户协议」；§8.2 增补 Q 项关闭记录；
3. `02_design/pages.md` P01 注册页：复选框（默认不勾选）+ 《用户协议》《隐私政策》链接（`/terms`、`/privacy`），未勾选时提交按钮禁用或提交即行内报错（文案：「请先阅读并同意协议」）；
4. `03_engineering/api-design.md` §4.1：`POST /auth/register` 入参增加 `agreedVersion`（或布尔 `agreed` + 服务端记录当前版本号）；未同意返回 `422 AUTH_005` 或新增 `AUTH_006`；
5. `03_engineering/architecture.md` §5.1：users 表增列 `agreedTermsVersion` / `agreedAt`（或独立 `user_consents` 表以支持后续政策更新再同意，推荐后者，含 `type`[terms/privacy/attachment]、`version`、`createdAt`，与 T6 共用）。

**验收标准**：

- Given 新用户，When 未勾选协议并提交，Then 注册被拒且提示指向协议入口；
- When 勾选并注册成功，Then DB 可查到该用户的 terms/privacy 同意记录（版本 + UTC 时间戳）；
- 隐私政策更新版本号后，存量用户下次登录被要求重新确认（复用 consents 表）。

### T2（P0）静态存储加密

**解决的问题**：R1——数据库与附件卷明文落盘，个保法第 51 条（三）加密义务未落实；附件可能含银行账号类敏感个人信息。

**方案选择（tech/ops 决策，评估师推荐 A）**：

- **方案 A（推荐）：宿主机全盘/分区 LUKS 加密**，覆盖 PG 数据目录与 `/data/attachments`；密钥/口令纳入 backup-dr §3.3 既有的「离线口令保管」机制（与 `.env` 解密口令同级管理，不与备份同存）。
- 方案 B（备选）：应用层对附件文件 AES-256-GCM 加密（StorageService put/get 内嵌），DB 不动——实现成本略高但可移植。

**修改位置**：

1. `03_engineering/architecture.md` §2 部署拓扑：宿主层标注「LUKS 加密卷（PG data + attachments）」；§7 横切关注点表「存储加密」行；
2. `04_ops/deployment.md`（宿主初始化步骤）：增加「磁盘分区 LUKS 格式化与挂载」步骤 + 密钥托管说明；
3. `04_ops/backup-dr.md` §3.1：备份内容清单第 2 条备注「源卷已静态加密，备份侧维持 AES-256 双保险不变」。

**验收标准**：重启宿主机需输入磁盘加密口令方可挂载数据卷；直接挂载/读取裸盘文件（模拟磁盘被盗）无法获得 PG 数据与附件明文；现有备份-恢复演练流程（backup-dr §4.1）在加密卷上复演一次通过。

### T3（P0）隐私政策与用户协议页面

**解决的问题**：R2 的「告知载体」。内容以 `07_compliance/privacy-policy-draft.md` 为基础，**经人工法务复核后定稿**。

**修改位置**：

1. `02_design/information-architecture.md` §2.2 路由表：新增公开路由 `/privacy`、`/terms`（无需登录），页脚全站常驻两链接；
2. `02_design/pages.md`：新增静态内容页规范（复用既有 tokens，移动/桌面自适应，版本号展示于页脚）；
3. `05_support/faq.md`：新增「我们如何保护你的发票数据 / 如何删除我的数据」条目（与隐私政策口径一致）；
4. 法务复核结论回填 `07_compliance/`（版本升级为正式稿）后，privacy-policy-draft.md 中 T2/T5/T7 依赖脚注方可移除。

**验收标准**：未登录浏览器可直接访问两路由；注册页（T1）与页脚链接可达；页面内容与 DB 同意记录的版本号一致；「待核实」事项（票面银行账号敏感定性等）已由人工确认。

### T4（P1）数据分类分级表

**解决的问题**：R6——数安法第 21 条分类分级制度未落实。

**修改位置**：`04_ops/`（建议并入 backup-dr.md 新增 §7 或独立 `data-classification.md`）：四级分类——L1 附件卷（可能含敏感个人信息）＞ L2 users/invoices 表 ≈ 会话 ＞ L3 events ＞ L4 日志；每级对应加密、备份、保留、清除、访问控制要求矩阵；声明「按当前业务形态不涉及重要数据，若二期引入企业协作/进项管理需重评」（该判断待核实，由复核人确认）。

**验收标准**：表覆盖架构 §5.1 全部存储对象；与 backup-dr 保留策略、architecture §6.5 清除流程无矛盾；被 ops 日常巡检清单引用。

### T5（P1）账号注销功能

**解决的问题**：R3——撤回同意与删除权（个保法第 15/47 条、网安法第 43 条）无账号级出口。

**修改位置**：

1. `01_product/features.md`：新增「注销账号」条目（建议 M2，若排期不下可先上「客服人工注销 SOP」兜底：support 文档 + ops 手工执行级联删除脚本，M3 前必须产品化）；
2. `03_engineering/api-design.md` §4.1：`POST /auth/account/deletion`（验证密码/二次确认）→ 冷静期（建议 7 天，期间可撤销）→ 到期 cron 物理删除：users 行、invoices 行、附件文件、sessions、events.userId 置空；错误码预留 `AUTH_006+`；
3. `03_engineering/architecture.md`：auth 模块职责扩展 + §6 新增「注销级联删除」数据流（复用 recycle 物理删除的事务纪律：先附件文件后 DB 行，孤儿对账兜底）；
4. `02_design/pages.md` 设置页 + `interactions.md` 新增流程（风险弹窗：注销不可恢复、请先导出、备份残留 14 天滚动过期的如实披露）；
5. `05_support/sop.md`：人工注销兜底 SOP（M1-M2 过渡期）。

**验收标准**：注销完成后，原账号标识在注册接口可重新注册；该用户全部发票/附件/埋点关联不可再被任何接口返回（404 或空集）；直接查库无该 users 行、invoices 行、附件文件；备份中残留仅存在于注销前生成的滚动备份并在 14 天内自然过期；support 具备人工兜底 SOP 并演练一次。

### T6（P1）附件敏感信息单独同意 + PIA 存档

**解决的问题**：R4——处理可能含敏感个人信息的附件缺单独同意（个保法第 29 条）与事前影响评估（第 55/56 条）。

**修改位置**：

1. `02_design/interactions.md` 上传流程（R7）前置：首次上传弹层（文案取 privacy-policy-draft 第二条），勾选后写 `user_consents(type=attachment)`；拒绝则关闭上传入口；
2. `03_engineering/api-design.md` §4.3：`POST /invoices/:id/attachments` 校验有效 attachment 同意记录，无则 `403/422`（新增 `ATT_004 无敏感信息同意`）；
3. `07_compliance/`：以 legal-assessment.md §2.2/§5.1-R4 为基础整理 PIA 记录（处理目的必要性、影响、措施）存档，此后每年或重大变更时复审（评估报告与处理记录至少保存三年，个保法第 56 条）。

**验收标准**：未完成单独同意的用户无法上传附件但可正常使用其他功能；同意记录可查（时间 + 版本）；PIA 记录文件存在于 `07_compliance/` 并含复核签字栏。

### T7（P1）备份对象存储限定境内

**解决的问题**：R5——backup-dr §3.4 候选含 Cloudflare R2 / AWS S3，境外区域将触发个保法第 38-40 条跨境提供全套义务。

**修改位置**：`04_ops/backup-dr.md` §3.4：将「首选对象存储版本化桶（OSS/S3/R2）」修订为「**限中华人民共和国境内区域的 OSS**（如阿里云 OSS 国内节点）；禁用境外区域（S3 海外/R2）」；补充云厂商委托处理协议签署要求（个保法第 21 条）与桶策略核查项（私有读写、TLS、版本控制、最小化凭证）。

**验收标准**：备份目标为境内区域且桶策略核查通过；如因故仍选境外区域，则已另行完成跨境合规程序并更新 privacy-policy-draft.md 第六条[^1]表述（评估师不推荐）。

### T8（P1）个人信息泄露通知应急预案

**解决的问题**：R8——个保法第 57 条通知义务无落地流程。

**修改位置**：`04_ops/runbook.md` 新增「个人信息安全事件」章节：事件分级（单账号/多账号/全量）、即时补救（隔离、改密、封禁）、**向履行个人信息保护职责部门的报告路径**、对用户的通知判断（能否有效避免信息危害——不能避免则必须通知）、留痕与复盘模板；与既有 P1 告警通道（monitoring）衔接。

**验收标准**：预案成文并经一次桌面推演（可与季度备份演练同日）；明确「谁在多少小时内对外报告/通知」的责任人与模板。

### T9（P1）CSV 导出提示

**解决的问题**：脱敏增强（低风险低成本）——导出物脱离产品控制后由用户自行保管，尽提示义务。

**修改位置**：`02_design/pages.md`/`interactions.md` R6：导出成功反馈增加常驻提示文案（「导出文件含完整发票信息，请妥善保管，避免转发他人」）；`05_support/faq.md` 对应条目。

**验收标准**：桌面/移动两端导出成功后均出现该提示（Toast 或下载栏横幅），文案与隐私政策口径一致。

### T10（P2，人工项）等保定级评估

**解决的问题**：R9——网安法第 21 条等级保护定级备案状态未定（待核实项）。

**动作**：由用户咨询当地主管部门或律师，确认面向公众的免费小规模服务是否需办理二级等保定级备案；结论记录回 `00_charter/decisions.md` 或 `04_ops/`。若需办理，排期在 M3 上线前。

**验收标准**：有书面结论（办/不办 + 依据）；若需办理，取得备案证明为 M3 发布门禁。

### T11（P2，pm 决策）全局隐私模式

**解决的问题**：抬头不脱敏口径下，公共场合旁窥面（个人抬头发票含自然人姓名时最大）。

**动作**：pm 将 design-spec §6.5「全局隐私模式」（一键掩码金额 + 号码）纳入 M2 议题池决策；不采纳则记录理由即可（现口径合规性评估结论为可接受，见 legal-assessment §6.4）。

**验收标准**：pm 决策记录在案（采纳排期 / 不采纳理由），design-spec §6.5 状态闭环。
