# 项目章程 —— 票夹通（网页版发票票夹管理）

> 项目 ID：P20260914-1728-网页版票夹管理发票 ｜ 章程版本：v1.0 ｜ 制定人：总规划师（主 Agent）

## 1. 项目名与一句话定位

**项目名**：票夹通（TicketWallet）

**一句话定位**：一个网页版"发票票夹"应用，让用户把自己开过的每一张发票集中收录、随时翻查——按时间、金额、抬头、类型检索，一目了然地回答"我到底开过哪些发票"。

## 2. 用户原始需求

> 我想做一个网页版本票夹管理，用户可以知道自己开过了哪些发票

需求解读（规划判断，供各角色对齐）：

- 核心动词是"**开过**"——面向的是用户**开出的发票**（销项/开票方视角），而非收进来的发票（受票方视角）；产品主场景是"我的开票记录台账"。
- "票夹管理"意味着**收录—组织—检索—回看**的完整闭环，而不是只读列表。
- "网页版"意味着以浏览器为载体的 Web App，桌面/移动浏览器自适应，暂不做原生 App。
- 隐含诉求：发票信息敏感，**数据私密性与账号隔离**是一等需求。

## 3. 目标（可衡量）

| # | 目标 | 度量 |
| --- | --- | --- |
| G1 | 用户可以录入开票记录（手工录入 + 发票关键字段结构化） | 首次录入到保存成功 ≤ 2 分钟 |
| G2 | 用户可以按月份/抬头/金额/类型/状态检索并翻看历史发票 | 任意筛选条件出结果 ≤ 1 秒（1000 条记录内） |
| G3 | 提供月度/年度汇总视图（张数、金额合计、类型分布） | 汇总页可一键导出 CSV |
| G4 | 数据私密：账号隔离 + 传输加密 + 敏感字段脱敏展示 | 安全清单全部落地（见 ops/support 文档） |
| G5 | 本期交付一个可部署的 MVP Web 应用 | 按执行计划 6 个职能阶段产出完备文档与脚手架 |

## 4. 范围

### 4.1 范围内（MVP）

- 账号体系：注册/登录/退出（邮箱或手机号 + 密码，一期不含第三方登录）
- 发票录入：手工表单录入（发票代码、号码、开票日期、抬头、金额、税额、类型、备注）
- 发票附件：支持上传发票图片/PDF 附件（单张 ≤ 10MB，每条记录 ≤ 3 个附件）
- 票夹列表：按时间倒序的全量列表 + 分页
- 多维检索与筛选：月份、抬头关键字、金额区间、发票类型（电子/纸质/专票/普票）、状态（正常/作废/红冲）
- 汇总统计：本年/本月张数与金额、类型分布图
- 导出：筛选结果导出 CSV
- 回收站：删除的记录进入回收站，30 天可恢复

### 4.2 范围外（明确不做）

- ❌ 税务局接口对接、真伪查验、自动勾选抵扣（合规接口复杂，二期评估）
- ❌ 发票图片 OCR 自动识别字段（二期做，一期手工录入）
- ❌ 原生 App / 小程序（只做响应式 Web）
- ❌ 多人协作/共享票夹（一期单用户私有）
- ❌ 对他人开票给我（进项）的管理——一期只管"我开出的"
- ❌ 支付、会员、商业化功能（财务角色仅做模型推演，不开发）

## 5. 成功指标

- **北极星指标**：周活跃用户中「本月新增开票记录条数」（周记录留存）
- 过程指标：注册→首条记录转化率 ≥ 60%；检索功能周使用率 ≥ 40%；导出功能月使用率 ≥ 20%
- 质量指标：核心接口 P95 延迟 < 500ms；可用性 ≥ 99.5%；录入表单一次提交成功率 ≥ 95%
- 口径定义由 pm 在 metrics.md 细化（埋点事件名与分母定义）。

## 8. 风险与兜底

| 风险 | 影响 | 兜底 |
| --- | --- | --- |
| 任一 subagent 产出未过质量门禁 | 文档缺失 | 重派一次 → 仍失败则主 Agent 按骨架补齐并记 degraded + issues，流程不中断 |
| 发票数据敏感引发合规疑虑 | 上线受阻 | 一期不做对外接口、字段脱敏展示、传输加密；合规评估列入 issues |
| OCR/查验接口不可得 | 功能缩水 | 已列为范围外，二期再议 |
| 单人维护的运维复杂度 | 稳定性 | ops 产出以"单机可落地"为底线方案，云托管优先 |
| 商业化不清晰 | 投入产出不明 | finance 仅做三场景模型，不做实际支付开发 |

## 9. 执行计划（阶段列表）

按依赖顺序执行，角色仅取自 AGENTS.md §2 注册表，pm 在最前：

2. **designer（UI/UX 设计师）** → `02_design/`：设计规范、信息架构、页面清单、交互流程、线框图
3. **tech（技术负责人）** → `03_engineering/`：技术选型、架构、仓库规划、API 设计、工程计划（repo-layout 物化为 scaffold/）

每阶段：派发 → 质量门禁校验 → （不合格重派/兜底）→ 知识库入库 → git 提交。
