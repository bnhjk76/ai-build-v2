## 1. 背景

### 1.1 用户原始需求

> 「我想做一个网页版本票夹管理，用户可以知道自己开过了哪些发票」

### 1.2 需求解读

- 核心动词是「**开过**」——产品面向用户**开出的发票**（开票方 / 销项视角），而非收进来的发票（受票方 / 进项视角）。主场景是「我的开票记录台账」。
- 「票夹管理」意味着**收录—组织—检索—回看**的完整闭环，而不是只读列表。
- 「网页版」意味着以浏览器为载体的响应式 Web App，桌面 / 移动浏览器自适应，不做原生 App。
- 发票信息涉及交易对手与金额，**数据私密性与账号隔离**是一等需求。

### 1.3 现状与替代方案的不足

当前目标用户管理「开出的发票」的主流做法及其痛点：

| 替代方案 | 存在的问题 |
| --- | --- |
| 纸质票夹 / 抽屉存放 | 易丢失、易褪色，无法检索与统计，交给会计时需手工誊抄 |
| Excel / 手机备忘录台账 | 字段不规范、多设备不同步、无附件归档、误删无法恢复 |
| 翻微信 / 邮件找开票记录 | 记录分散在多处，按抬头或金额找一张票平均耗时超过 10 分钟 |
| 依赖开票软件（税控 / 数电平台）导出 | 只覆盖某一渠道开出的票，代开、纸质、多渠道场景无法统一归档 |

结论：市场上缺少一个**轻量、私有、跨渠道**的「我开出的票」的个人侧台账工具，这就是票夹通的切入点。

## 2. 目标用户

### 2.1 画像 P1：个人开票者（自由职业者 / 个人代开者）

- **身份**：设计师、讲师、咨询顾问、灵活就业者，通过税务局代开或平台开票向客户收款。
- **行为特征**：开票频次不固定（月均 1–10 张），票据散落在代开大厅、邮箱、微信里。
- **典型诉求**：「这个月我到底开了几张票、多少钱？」「客户说没收到票，我开过没有？」
- **设备**：手机浏览器为主，偶尔桌面。

### 2.2 画像 P2：小微商户 / 个体户老板

- **身份**：个体餐馆、工作室、小门店的经营者，使用税控设备或数电平台给客户开票。
- **行为特征**：月均开票 10–200 张，月底需要与对账单核对，并导出明细交给代理记账会计。
- **典型诉求**：「月底把本月开的票汇总导出给会计」「按客户抬头查某一批票」「错开的作废票也要留痕」。
- **设备**：桌面浏览器为主。

### 2.3 非目标用户（反画像）

- 需要管理**进项发票**（收到的票）并进行抵扣勾选的企业财务——一期不做进项与税局对接。
- 需要**发票真伪查验**、自动验真的用户——一期无税局接口。
- 需要多人协作共享票夹的团队——一期单用户私有。

## 3. 核心痛点

| # | 痛点 | 影响 | 票夹通的解法 |
| --- | --- | --- | --- |
| PT1 | 开过的票散落各处，说不清「我到底开过哪些」 | 对账、报税、答疑时临时翻找，耗时且易遗漏 | 统一票夹：全部开票记录按时间倒序集中沉淀 |
| PT2 | 缺乏结构化字段，无法按条件快速定位某张票 | 只能逐条肉眼翻找 | 多维检索：月份 / 抬头关键字 / 金额区间 / 类型 / 状态，1 秒出结果 |
| PT3 | 月度、年度汇总靠手工累加 | 数字不可信，与会计口径对不上 | 汇总统计：本年本月张数金额、类型分布，一键导出 CSV |
| PT4 | 票面文件（图片 / PDF）与台账分离 | 台账有了但「票」找不到 | 每条记录可挂附件（≤3 个，单张 ≤10MB），记录与票面同址存放 |
| PT5 | 误删记录后无处可寻 | 台账出现黑洞，对账差异无法解释 | 回收站：删除后 30 天内可恢复 |
| PT6 | 发票数据敏感，担心泄露 | 不敢用线上工具 | 账号隔离 + HTTPS 传输加密 + 敏感字段脱敏展示 |

## 4. 价值主张

**一句话**：票夹通是你的私人「销项发票票夹」——把开过的每一张发票集中收录、随时翻查，按时间、金额、抬头、类型一搜即得。

三支柱：

1. **记得全**：2 分钟内完成一条开票记录的结构化录入，并可附票面文件，跨渠道（代开 / 税控 / 数电）统一归档。
2. **找得快**：多维筛选 1 秒出结果（1000 条内），回答「我开过哪些发票」不再靠回忆。
3. **算得清**：本月 / 本年张数与金额、类型分布自动汇总，CSV 一键导出交会计；误删可恢复，敏感信息脱敏展示。

## 5. 产品目标（对齐章程 G1–G5）

| # | 章程目标 | PM 口径细化 | 验收里程碑 |
| --- | --- | --- | --- |
| G1 | 首次录入到保存成功 ≤ 2 分钟 | 从点击「新增发票」到保存成功返回列表的端到端耗时（新用户首次操作） | M1 |
| G2 | 任意筛选条件出结果 ≤ 1 秒（1000 条内） | 前端发起查询到列表渲染完成；数据量为单账号 1000 条记录 | M1 |
| G3 | 汇总视图 + 一键导出 CSV | 本年 / 本月张数金额、类型分布；筛选结果与汇总明细均可导出 CSV（UTF-8 带 BOM，Excel 直接打开不乱码） | M2 |

| G5 | 交付可部署 MVP（文档 + 脚手架） | 本流程（M0）产出 6 个职能阶段完备文档与脚手架，M1–M3 由后续开发会话实施 | M0 |

## 6. 范围边界

### 6.1 MVP 范围内（与章程 4.1 一致）

1. **账号体系**：注册 / 登录 / 退出（邮箱或手机号 + 密码；不含第三方登录、不含找回密码——找回密码为 M2 后补充项，见 8.2 待确认）。
2. **发票录入**：手工表单录入结构化字段——发票代码、号码、开票日期、抬头、金额、税额、类型（票种：专票/普票 × 介质：电子/纸质）、状态（正常/作废/红冲）、备注。
3. **附件上传**：发票图片或 PDF，单张 ≤ 10MB，每条记录 ≤ 3 个。
4. **票夹列表**：按开票时间倒序 + 分页 + 记录详情。
5. **多维筛选**：月份、抬头关键字、金额区间、类型（电子/纸质/专票/普票）、状态（正常/作废/红冲），多条件组合。
6. **汇总统计**：本年 / 本月张数与金额、类型分布。
7. **CSV 导出**：当前筛选结果导出 CSV。
8. **回收站**：删除记录进入回收站，30 天内可恢复，到期自动清除。

### 6.2 范围外（明确不做，与章程 4.2 一致）

| # | 不做项 | 原因 | 二期去向 |
| --- | --- | --- | --- |
| O1 | 税务局接口对接、真伪查验、自动勾选抵扣 | 合规接口复杂、资质门槛高 | 二期评估 |
| O2 | 发票图片 OCR 自动识别 | 识别准确率与人力投入，一期手工录入保证确定性 | 二期规划 |
| O3 | 原生 App / 小程序 | 只做响应式 Web，控制成本 | 视数据决策 |
| O4 | 多人协作 / 共享票夹 | 一期单用户私有，简化权限模型 | 二期评估 |
| O5 | 进项发票（他人开给我的）管理 | 一期只管「我开出的」，保持产品焦点 | 二期评估 |
| O6 | 支付、会员、商业化功能 | 财务角色仅做模型推演，不开发 | 视单位经济决策 |

### 6.3 里程碑映射

- **M1（MVP 核心）**：账号 + 录入 + 列表 + 检索（覆盖 G1、G2、G4）。
- **M2（完整功能）**：汇总 + 导出 + 附件 + 回收站（覆盖 G3，补全 G4 脱敏细节）。
- 功能与里程碑的逐条映射见 `01_product/features.md` §2。

## 7. 关键非功能需求（产品侧底线）

- **安全**：全站 HTTPS；密码不可明文存储（哈希方案由 tech 定）；会话过期后需重新登录；用户间数据严格隔离（任意接口不可越权访问他人记录）。
- **性能**：核心查询接口 P95 < 500ms（质量指标，与章程 §5 一致）；列表筛选 ≤ 1 秒（1000 条内）。
- **兼容**：主流浏览器（Chrome / Edge / Safari / 微信内置浏览器）最新两个大版本；桌面与移动端自适应布局。
- **可用性**：≥ 99.5%（月度）。
- **数据保留**：回收站 30 天；账号内正常记录永久保留（直至用户删除）。

## 8. 关键假设与待确认清单

### 8.1 已采用的合理假设（无碍主线，可迭代）

- A1：发票「类型」按两个维度建模——票种（专票/普票）× 介质（电子/纸质）；列表筛选项呈现为章程所述的「电子/纸质/专票/普票」四项，分别映射到对应维度。
- A2：数电发票（全面数字化电子发票）无「发票代码」，故发票代码设为选填；发票号码为必填（8–20 位数字，兼容数电 20 位）。
- A3：汇总口径——「有效张数/有效金额」只计状态为「正常」的记录；「红冲」记录按票面金额（负数）冲减有效金额；「作废」记录不计入有效金额仅计总张数。
- A4：金额区间筛选作用于「价税合计」（= 金额 + 税额，直观口径）。
- A5：登录态保持 7 天；连续 5 次密码错误锁定账号 10 分钟（防爆破底线）。
- A6：列表每页 20 条；CSV 单次导出上限 5000 条。

### 8.2 待确认（需人工 / 后续阶段拍板）

- Q1：是否需要「忘记密码 / 重置密码」功能？章程未列入 MVP，但上线后将成为客服高频问题——建议 M2 前补入（已同步 support 角色预案）。
- Q2：脱敏字段范围——PM 底线为「发票号码（保留末 4 位）+ 账号手机号/邮箱」，抬头是否脱敏由 designer 在界面层权衡可用性后确定。
- Q3：北极星指标采用「总量口径」还是「人均口径」作为主口径（metrics.md 两个口径均已定义，默认主口径为总量，辅助看人均）。
